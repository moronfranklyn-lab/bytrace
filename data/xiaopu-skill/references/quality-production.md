## 使用时机

在准备起草、保存草稿、规划图片、审查全文、生成图片、发布文章或跨 Claude/Codex 交接时读取本文件。实际生图还必须读取 `visual-production.md`。

本文件管理生产，不替代 `insight-argument.md` 的内容判断和 `composition-voice.md` 的声音判断。

## 自适应生产档位

根据材料成熟度、事实风险、洞察新颖度和篇幅复杂度选择档位。不要只按字数判断。

### Fast

适用于短评、标题、局部改稿和观点证据都很清楚的短内容。

- 在对话中保存最小主张、证据、边界和反方。
- 直接给结果，不创建工作区，除非小普要求落盘或需要跨工具交接。
- 仍要规划封面和至少一张真正承担解释作用的内文图；正文定稿前只留占位，不生图。
- 通常只在核心判断或个人事实不清时确认一次。

### Standard

适用于大多数工具分享、产品分析、个人叙事和教程。

- 建立紧凑 `文章简报.md`，保留证据、洞察、论证、事实缺口和图片机会。
- 完成 Pass A、Pass B 和 Pass C，批量询问高价值缺口。
- 需要落盘、持续多轮或配图交接时建立工作区。
- 显式确认通常控制在核心判断和最终稿两个位置，不逐章审批。

### Deep

适用于深度产品报告、方法论、来源密集的趋势判断和可能影响他人重大选择的建议。

- 完整建立来源、身份账本、候选解释、主张证据图、反方和边界。
- 比较结构候选，进行成文前与成文后两轮压力测试。
- 建立工作区并维护唯一的规划和正文来源。
- 计划内确认点最多三个：核心判断、结构与证据缺口、最终稿。小普要求更细共创时再增加。

档位可以升降级。发现关键事实风险时升级；已有成熟材料且只需编辑时降级。

以上确认点数量只约束写作阶段。进入正文定稿后的视觉生产时，封面与第一张内文图的风格确认，以及是否继续生成其余图片，是独立硬闸门，不能为了压缩轮次省略。

## 共创与确认点

共创指小普拥有判断权、身份事实和最终编辑权，不等于必须分章节慢慢写。

- 小普要求完整初稿时，在材料允许的情况下直接给完整初稿。
- 小普只想讨论方向时，不抢跑写全文。
- 已经提供过的信息直接使用，不让小普再填一遍表。
- AI 可以提出候选判断、结构甚至完整表达，但涉及小普立场、真实经历和情绪时保留确认边界。
- 把缺口按重要性批量提出，优先影响核心判断和真实性的问题。
- 只有不同选择会明显改变文章时，才单独请求决定。

若材料不足但小普仍要完整初稿，使用清楚的待确认标记，不补造个人事实。交付时集中列出这些标记，不在每段重复解释。推荐或实测分支缺少真实任务、结果和证据痕迹时，可以继续交付候选洞察、完整测试计划、公开资料段、带证据状态的长文大纲或 `status: evidence_pending` 的内部工作稿，不能把待确认占位包装成可发布全文。

## 文章工作区

先区分路径角色，不能把安装路径、维护源和文章输出混在一起：

| 角色 | 路径 | 规则 |
|---|---|---|
| Skill 维护源 | `Skills/xiaopu-writing/` | 修改、回归测试和版本比较以此为准 |
| Codex 运行副本 | `~/.codex/skills/xiaopu-writing/` | 只有小普明确要求同步时才由维护源覆盖 |
| 文章根目录 | `/Users/ahai/Library/Mobile Documents/com~apple~CloudDocs/Documents/XIAOPU/文章/` | 正式正文与正式插图的输出位置 |
| 单篇工作区 | `文章/临时工作区/<article-id>/` | 简报、正文别名、视觉清单和生产资产 |

不要把文章输出到 Skill 目录，也不要因为维护了备份源就自动同步 Claude、Codex 或其他安装副本。只同步小普本轮点名的目标。

需要工作区时，为每篇文章使用独立子目录：

```text
文章/临时工作区/<article-id>/
├── 文章简报.md
├── 草稿.md
├── 配图交接.md
└── imgs/
```

- `文章简报.md` 是编辑判断、证据门槛、四条状态轴和未决项的权威来源，只保留视觉摘要。
- `canonical_body_path` 指向唯一权威正文。`草稿.md` 可以就是该文件，也可以是明确登记的符号链接别名；禁止维护两份独立全文。
- `配图交接.md` 是逐图视觉清单、风格契约、素材哈希、审批事件和修复记录的权威来源。简报不再复制一份可独立变化的逐图清单。
- `imgs/` 只存放通过质检的文章资产；系统图像生成目录和临时修复图不能充当最终交付目录。

工作区成图使用全库唯一文件名，例如 `<article-id>-cover.png` 和 `<article-id>-fig-01-<short-name>.png`。正式发布前复制到 `文章/插图/`，确认存在后再写成 Obsidian 引用，避免不同文章的 `cover.png` 相互冲突。

四条状态轴不能合并成一个模糊的 `stage`：

- `content_status` 只回答正文是否仍在改。小普说“正文定稿”“文章写完了”时可设为 `locked`，不自动改变其他三条轴。
- `testing_status` 只回答真实测试与主张级证据是否达到发布门槛。解释图已经生成、正文写得完整，都不能替代它。
- `visual_status` 只回答视觉生产走到哪一步。正文锁定后可以先完成生成型解释图，即使真实证据仍在等待；此时使用 `evidence_waiting`，不能用生成图补齐证据。
- `publication_status` 是派生结论，不凭感觉手填。只有正文锁定、测试门槛通过或不适用、所有已采用视觉任务均为 `ready` 或 `declined`、文件与哈希一致、发布检查通过，才可设为 `ready`；实际发布后才是 `published`。

不要自动清空 `文章/临时工作区/`。开始新文章时创建新子目录，不覆盖上一篇。需要整理旧目录时，先检查内容并获得明确删除或归档授权。

## 配图规划、占位与生产闸门

每篇文章都要经过一次视觉机会扫描，规划一张封面和至少一张真正承担解释作用的内文图，并在草稿中保留建议配图占位符。除这组基础视觉外，其余建议由小普决定采用哪些；不要按字数设置固定图片数量。

草稿阶段只做规划。正文没有经过语义终审、机械检查并由小普明确确认定稿时，禁止生成封面或任何内文图。实际生成、IP 参考、构图、Pilot 确认和质检按 `visual-production.md` 执行。

推荐与实测文章例外：额外解释图仍由小普决定，但正式稿至少要有一条真实测试证据痕迹，如截图、脱敏日志、输出文件或可复现输入输出。若文章尚在草稿阶段，保留证据占位并明确需要小普补什么；生成图不能替代。

图片只承担三类工作：

1. **证明**，用真实截图、后台、过程记录、结果或来源图支持主张。
2. **解释**，用流程图、关系图、分层图、时间线、对比矩阵或框架图降低理解成本。
3. **减负**，在高密度长文中用有信息量的视觉帮助扫描，不用纯装饰图填配额。

在草稿阶段使用可见占位符：

```text
【建议配图｜截图｜证明实际测试结果｜需要小普提供产品版本与完整界面】
【建议配图｜对比矩阵｜解释四种工具组合的取舍｜基于正文的任务、耗时、稳定性和适用输入】
```

每个占位符写清：

- 图片类型。
- 它服务的正文主张。
- 画面必须包含的元素、层级、关系或关键节点。
- 素材来源和真实性要求。
- 隐私、版权、脱敏或时效风险。

小普确认采用后，先在视觉清单把状态改为 `accepted`；这只表示决定采用，不表示素材已经就位。缺少真实素材时使用 `waiting_source`。只有图片实际生成或真实素材就位并通过质检后，才改为 `ready` 并换成正式 Obsidian 图片引用：

```text
![[<article-id>-fig-01-四种方案对比.png]]
![[<article-id>-evidence-01-实际测试结果.png]]
```

真实产品界面、后台和结果优先使用真实截图。没有真实截图时保留“待小普截图”，不能悄悄生成示意图冒充实测。需要脱敏示意图时明确标注其性质。

避免图文重复。图已经完整表达关系时，正文只说明它与判断的连接，不再逐项复述。

`配图交接.md` 为每张已采用图片记录：

```yaml
- id:
  placeholder:
  role: cover | internal | evidence
  type: screenshot | diagram | chart | timeline | comparison | illustration | other
  visual_mode: generated | real_screenshot | source_figure | composite
  function: explain | prove | relieve
  supports_claim:
  text_anchor:
  required_elements: []
  forbidden_elements: []
  ip_role:
  ip_decision_reason:
  source_material:
  privacy_or_copyright:

```

从占位到成图必须经过以下闸门：

```text
语义终审和机械检查
  -> 小普确认正文定稿
  -> 记录最终标题和正文 SHA-256
  -> Pilot 前复读正文并校验 SHA-256
  -> 确认 IP 参考图与视觉清单
  -> 分别生成封面、第一张生成型内文图
  -> 展示两张 Pilot，主动给出微调建议
  -> 等待小普确认风格
  -> 明确询问是否生成其余已采用配图
  -> 剩余批次前再次复读正文并校验 SHA-256
  -> 获得确认后一次完成其余图片
  -> 将每项收敛为 ready、waiting_source 或 declined
  -> 证据素材就位后质检、复制到文章/插图、替换占位
  -> 运行工作区发布检查与文章发布 lint，核对文件存在并复读全文
```

“一次完成其余图片”是一次授权和一个连续生产阶段；每张不同图片仍然单独调用图像生成，避免把多个独立构图塞进一张输出。

## 语义终审

按以下顺序审查。前一层有根本问题时，先修复再继续。

### 1. 真实性

- 第一人称动作、结果、情绪、对白和动机是否有来源。
- 时效性事实是否按当前日期核验。
- 事实、推断、类比和假设是否清楚区分。
- 外部数字是否有可回查来源、时间和口径。

### 2. 洞察与论证

- 核心判断是否超出证据范围。
- 每条关键证据究竟证明了什么。
- 最强反方是否被公平处理。
- 因果链是否完整，是否存在更简单解释。
- 读者最终获得了新的理解、选择、行动、验证能力或可复用物；文章是否在只交付一个判断时过早结束。

### 3. 结构

- 开头是否快速建立可信接近性和核心矛盾。
- 相邻读者是否能从共同利益进入，专业概念出现前是否补了必要前提。
- 每一部分是否回答读者问题链中的一个问题，并增加不同层级的收益。
- 后半段是沿同一问题继续下钻，还是没有连接的横向换题；不要仅因跨越技术、商业或方法论就误判跑题。
- 是否有背景过长、案例漂浮、重复收益或新议题突然出现。
- 如使用结构化框架，是否最多只有一个主框架和一个辅助框架；有没有把第三套结构改名成清单、流程或评测法后继续独立编号。
- 标题承诺是否由正文兑现。
- 结尾是否回到核心问题，而不是总结和拔高。

### 4. 小普声音

- 第一人称是否承担证据或判断责任。
- 是否靠口癖、短句配额和网络热词模仿小普。
- 是否存在报幕式过渡、重复判断、段尾升华和做作画面。
- 时间和版本是否写成小普自然会说的“今年、去年、26年、这次”和产品短名，而不是因为输入材料很精确就逐字贴进正文；普通开头是否仍残留四位年份、完整日期或构建号。
- 哪一段仍然是“任何懂 AI/产品的模型都能写”的通用内容。

### 5. 配图

- 是否完成了视觉机会扫描并留下建议占位符。
- 每张建议图是否服务一个明确主张。
- 是否把示意图误当真实截图，或遗漏隐私、版权和脱敏风险。
- 真实证据截图是否保持原始像素或只经过确定性脱敏与排版，没有被图像模型重绘。
- 是否存在图文重复和失效外链。
- 是否错误地在正文定稿前生成了封面或内文图。
- 如已进入视觉生产，视觉清单是否引用最终正文，封面和第一张内文图是否先经过风格确认。
- 内文图主体组是否垂直居中，上下留白是否只是必要安全边距；是否因底部或顶部过空导致视觉中心漂移。

## 推荐与实测发布闸门

文章包含推荐、对比、实测、最佳、替代、覆盖比例或选型结论时，前期必须已经读取 `recommendation-testing.md` 并建立测试卡；本节在语义终审后只做复核。文章中途新增这类结论时，立即回退补测试卡，不等到终审才处理。

- 证据等级是否足以支持标题和结论，没有用公开资料冒充亲测。
- 真实任务、测试条件、成功标准、实际结果，以及失败、限制、边界或人工接管是否完整；没有观察到失败时是否如实说明样本限制。
- 小普是否确认“我测了、我发现、我推荐”对应的事实、体感和最终判断。
- 比较是否基于同任务和可说明的条件；单位价格是否被错误当成成功任务总成本。
- 正文是否有一条原创证据痕迹，生成图是否被错误用于证明实测。
- 推荐是否同时给出适合与不适合对象，以及低成本开始和验证方式。
- 工具、开源项目或 Skill 是否检查版本、许可证、权限、依赖、数据去向、维护与安全风险。
- 完整日期、版本和环境是否在内部可回查，正文是否只在复现需要的位置出现一次精确信息。

关键材料不足时回到共创测试，不发布一篇靠免责声明或语气代替证据的推荐稿。

## 机械检查

语义终审后再运行：

```bash
python3 scripts/lint-article.py <文章路径>
```

这条命令允许草稿保留完整的建议配图占位。准备发布时必须改用：

```bash
python3 scripts/lint-article.py --publication <文章路径>
python3 scripts/validate-workspace.py --profile release <工作区路径>
```

脚本只发现确定性的发布风险和高风险表达，不判断原创性、自然度、证据是否够强或文章是否“像小普”。不要为了让机器零告警而改坏准确引语和自然语法。

逐项处理：

- 未解决的事实或个人信息标记必须清掉、补齐或明确保留为内部草稿。
- 图片占位符格式必须完整；发布稿不得保留任何建议配图占位，已拒绝建议直接删除。
- 发布稿中的正式图片引用必须指向已经存在并通过质检的文件；不能把 `accepted` 或生成中的任务写成已完成图片。
- 高风险 AI 套话和批量节奏符号需要人工看上下文后重写或说明保留原因。

## 文件安全与发布

文件操作遵守以下硬约束：

- 写入前读取目标文件和同主题文件，确认当前权威版本。
- 新建、整篇重写和局部修改必须区分。局部修改只改变必要范围。
- 发现同主题多个文件时先停下，确认哪份是权威版本。
- 重命名前检查目标文件是否已存在，明确源和目标，再执行安全重命名并复核。
- 不静默删除工作区、旧稿、图片或来源文件。
- 正文锁定后如发生实质修改，按 `visual-production.md` 复核受影响图片，不让旧图静默沿用。
- Pilot 和剩余图片两个批次开始前都重新计算并核对正文 SHA-256。
- 保存后重新读取关键段落，确认内容和路径正确。
- 内容定稿只锁定 `content_status`。不要因“小普说文章写完了”就跳过测试、视觉资产或发布检查。

## 异常处理

- **来源冲突**：保留两种口径及差异，优先原始来源，必要时缩小结论。
- **个人事实缺失**：使用待确认标记并集中询问，不合成情绪或经历。
- **核心判断证据不足**：补证、降级为观察、缩小边界或删除，不强化语气。
- **推荐或实测证据不足**：先输出最小测试矩阵并与小普共创真实测试，不用“未同环境实测”声明替代，也不把待测假设写成第一人称结论。
- **截图不可用**：说明需要什么真实素材；可做脱敏示意图时明确它不是实测截图。
- **正文尚未定稿却要求试图**：保留视觉方案和提示词，说明硬闸门，先完成正文确认。
- **IP 参考图不可用**：封面和当前 `ip_role` 需要人物的图片停止生图；小普重新上传或确认原图后，先恢复到 `assets/ip/xiaopu-ip-reference.png` 并检查内容，再继续生产，不按文字近似重建。`ip_role: none` 的内文图不受影响。
- **Pilot 尚未确认**：保持未确认图片为 `style_review` 并具体询问；只有小普给出修改方向时才调整，不自行修改，也不生成剩余图片。
- **正文完成但证据未完成**：设为 `content_status: locked`、`publication_status: blocked`，继续保存真实证据任务和主张门槛，不把“写完”误报成“可发布”。
- **真实素材尚未提供**：将已采用任务标成 `waiting_source`，不让 `accepted` 同时表示“已选择”和“仍缺素材”。
- **工作区已有内容**：创建新文章子目录或请求处理方案，不覆盖、不清空。
- **发布文件冲突**：停止写入，列出冲突路径并请小普指定权威版本。
- **用户中途改变方向**：更新简报和正文唯一来源，废弃内容保留在版本记录或对话中，不让两套主张并存。
