## 0. 一句话定位

**把一个模糊的写作思路，用「拆解过的博主风格」写成一篇有论证骨架的多平台成稿。**

## 1. 目标用户与核心任务

### 1.1 目标用户

| 维度 | 事实 |
| --- | --- |
| 是谁 | **单人使用**。当前实例的机器路径、CLI 订阅、API key 全指向同一台 Mac（`lib/claude.ts` 硬编码 fallback 路径可证） |
| 身份 | 公众号 / 多平台内容创作者，同时具备 AI 产品背景（语料库 22 篇已发表文章 + 「AI 产品经理」主题可证） |
| 技术能力 | 能开终端、能填 `.env`、能看懂 `tsc` 报错；但**不愿意每次写文章都手搓 prompt** |
| 使用频率 | 按需，非高频。典型节奏是"攒了几个想写的点 → 一次性拆博主 + 产文" |
| 人机比 | **1:1**（一个用户对一个本机实例），无并发、无多租户 |
| 交互形态 | **同步流式**。用户盯着屏幕看正文一个字一个字出来，随时能中止 |

### 1.2 核心任务

> 在**不联网把稿子交给第三方 SaaS** 的前提下，把「一段思路 + 我喜欢的博主风格 + 目标平台口味」变成**可以直接发的成稿**。

支撑这个任务的三个子任务：

1. **学风格**——把喜欢的博主的文章拆成可复用的结构化「风格指纹」（而不是每次凭感觉描述"我想要半佛那种感觉"）。
2. **学平台**——把目标平台（公众号 / 知乎 / 小红书 / 少数派…）的板块口味拆成「站点画像」。
3. **按骨架写**——先出有论证骨架的大纲（每节有 thesis 和 depth_role），确认后再流式扩写成正文。

### 1.3 明确不服务的场景

- ❌ **多人协作 / 团队共用**——无账号体系、无权限、无并发控制（`data/autoarticle.db` 是单机文件）
- ❌ **对外提供服务**——数据全留本机，不做 SaaS（这是项目铁律，写在 `CLAUDE.md`）
- ❌ **自动发布到平台**——只产出成稿 + 导出格式，发布动作留给人
- ❌ **无脑批量产文**——见 §7.3 反爬边界，工具主动限制批量抓取

## 3. Agent 的主链路

### 3.1 主链路形态

**分步确认式，不是一次生成，也不是多轮对话。**

```
选平台 → 写思路 →[确认]→ 挑风格 → 微调 → 出大纲 →[确认]→ 流式正文 → 预览导出
                                          ↑
                                    唯一强制闸门
```

判定依据：`app/compose/page.tsx` 用显式 `step` 状态机（`useState<Step>(1)`，`setStep()` 单向推进，可回退），且 Step 5 与 Step 6 之间是硬边界（`onNext={() => setStep(6)}` 只在用户点确认后触发）。

### 3.2 三个 Agent 子链路的真实编排

#### ① 风格指纹拆解（`/api/fingerprint/v3`）

**多阶段流水线 + 多 agent 并行**，SSE 事件名反映真实阶段（`open → stage → article → warn → chunk → done`）：

| Stage | 做什么 | 模型档位 |
| --- | --- | --- |
| Stage 0 | 文章自动分类（8 个固定白名单类别，**不让模型自由分类**） | 分析类 |
| Stage 1 | 逐篇抽取：12 维度 + `structure_shape`(6选1) + `depth_layers` + `depth_chain` + `concrete_analogies` | 分析类 |
| Stage 2 | 汇总成 `structure_repertoire` / `depth_pattern` / `analogy_bank` | 分析类，**timeout 480s** |
| Stage 3 | 跨平台对比报告 | 分析类，timeout 360s |
| Category Profile | 单类别样本 ≥ 3 篇时生成该类别专属配方 | 分析类，timeout 360s |

**关键约束**：`concrete_analogies` 强制**物件级**（"户口本进 iCloud"），禁止抽象隐喻（"如同登山"不算）。

#### ② 写作链路（`/api/compose/outline` + `/draft` + `/refine`）

- **outline**：流式，事件 `open → chunk → done / error`。必须输出 `core_thesis` + `structure_shape` + 每节 `thesis` / `depth_role`。
- **draft**：流式，**多平台串行**（不是并发——本机 CLI 是订阅制，并发会撞限速）。事件序列：
  `open → platform_start → delta → (critic_start → critic → critic_error → critic_best_of_n → rewrite_start)* → platform_done → done / error`
  单平台失败不阻断后续平台（继续跑 + 收集到 `errors[]`）。
- **critic reflection loop（v3.4）**：草稿落地后打分，`CRITIC_PASS_THRESHOLD = 20`（满分 25，5 维 × 5 分：结构/深度/类比/金句/禁忌），`CRITIC_MAX_ATTEMPTS = 3`（= 最多 2 次重写）。不达标带 hint **全文重写**（不做按节修补——边界识别太脆）；critic 失败 **fail-open** 不阻塞，用原稿落库。证据：`lib/prompts/critic.ts:49,51`。
- **refine**：润色，流式。

## 4. 什么算「生成得好」

### 4.1 机器可判的标准（已在代码里执行）

**critic 五维打分，满分 25，≥ 20 通过**（`lib/prompts/critic.ts`）：

| 维度 | 判什么 |
| --- | --- |
| 结构 | `structure_shape` 是否贯彻；`depth_role` 是否有 `deeper` 且非全 `parallel` |
| 深度 | 是否沿读者问题链下钻，而不是平铺列举 |
| 类比 | 是否用了博主 `analogy_bank` 里的**具象物件**，而非抽象隐喻 |
| 金句 | 是否有记忆点且不堆砌 |
| 禁忌 | 是否触犯 AI 腔、编造第一人称经历、标题超出正文证据 |

### 4.2 定性的「好」

从 `lib/prompts/xiaopu-writing.ts`（写作规则常量）反推出的产品级好稿标准：

1. **洞察解释真实矛盾**，而不是把行业共识换个说法。
2. **每节首段回扣上节 thesis**，沿同一条问题链下钻，并交付新的理解 / 选择 / 行动 / 验证收益。
3. **抽象论点必须配物件级类比**——这是全项目的灵魂底线。
4. **第一人称只承担真实亲历/判断/选择责任**，不编造动作、情绪、对白、现场细节。
5. **没有 AI 腔**：删报幕式过渡、段尾升华、万能暖场、空泛形容词、重复判断。
6. **事实后立即给判断**；给数据补口径；失败写完整（预期 → 现象 → 根因 → 修复 → 新规则）。
7. **标题承诺不超过正文证据**；结尾回扣核心矛盾，不突然上升成时代宣言。

### 4.3 允许什么瑕疵

| 瑕疵 | 容忍度 | 依据 |
| --- | --- | --- |
| 个别标点/排版错误 | ✅ 可接受 | 导出后可手改 |
| 未通过 critic 的稿子 | ⚠️ 会保留（fail-open + best-of-N） | 不阻塞交付，但会标记评分 |
| 事实数字有出入 | ❌ **不可接受** | 所以有事实底座机制 + 跨模型审查 |
| 编造第一人称经历 | ❌ **红线** | 写进 critic 禁忌维度 + article prompt 硬约束 |
| 抽象隐喻偷懒 | ❌ **红线** | v3.3 核心约束，prompt 硬规定物件级 |

### 4.4 谁来判断

| 判断者 | 判什么 |
| --- | --- |
| **critic（模型）** | 日常自动把关：五维打分，不达标自动重写 |
| **用户（你）** | 最终判断：Step 5 看大纲、Step 6 盯流式、Step 7 看预览。**你是唯一有权说"这篇可以发"的人** |
| ~~codex（跨模型）~~ | ~~仅 `/research` 链路~~ **该链路已删除** |

> **待确认**：目前**没有**做过"5–10 条真实样例人工打分"来校准 critic 的阈值。`CRITIC_PASS_THRESHOLD = 20` 是工程设定值，不是用真实样例标定出来的。建议在方案二冒烟时补这一步。

## 6. 模型与成本约束

### 6.1 现状（代码事实）

| 用途 | 当前走什么 | 模型档位 |
| --- | --- | --- |
| 正文 draft + refine | 本机 Claude CLI 订阅 | **Sonnet 4.6**（`ARTICLE_MODEL`，为降 AI 味刻意降档） |
| outline / critic / 指纹分析类 | 本机 Claude CLI 订阅 | CLI 默认（Opus 档，为结构强度与评审严格度） |
| 事实搜集（gather 事实底座） | `lib/claude.ts` 的 `codex-cli` provider 分支 | Codex CLI 订阅 |
| 配图视觉打标 | 本机 Claude CLI 挂 Read 工具 | 一次性短任务，约 14s/张 |

**铁律（`CLAUDE.md` 明文）**：不接 Anthropic API、不带 key、不联网调 LLM——因为**已付订阅费，不付双份**。

### 6.2 本轮转向

方案二要把 **① 主 Agent** 与 **② 联网事实搜索** 两组改成 **`.env` 可配 API**，**但保留本机 CLI 兜底**——填了就走向量 API，不填就继续走订阅。这意味着从"单一订阅模式"变成"订阅或 API 二选一，按功能分组"。

> **⚠️ 范围收缩**：原本计划的第三组「深度调研」**随 `/research` 链路删除而取消**（见 §3.2 ③ 的警告框）。

### 6.3 成本上限

> **待确认**：现在的代码**没有任何成本上限或用量护栏**。历史上唯一一次成本事故是 Apify（2026-05-24 单次拆解被扣 $4.91/$5）——**但该模块现已从工作树删除**（见 §6.4），所以爬虫侧成本风险已解除。
> **剩下的空缺是模型侧**：主 Agent / 搜索 / 调研改成 `.env` API 后，会产生按量计费的真实花费。**建议方案二补一个会话级累计计数器 + 单次上限**。

### 6.4 爬虫通道与平台价格约束（已调研，记录防重蹈）

> **⚠️ 现状变更**：Apify 相关模块**已从工作树删除**——`lib/crawler/apify.ts`、`lib/apify/usage.ts`、`app/api/apify/usage/route.ts`、`components/nav/ApifyStatusPill.tsx`（`git status` 显示为 `D`）。
> 爬虫现在只走 **OpenCLI（借登录浏览器）→ cheerio 本地解析** 两级，最后兜底是提示用户直接粘贴正文。**零 API 成本、零 token 成本。**
> 下表保留的是当时的调研结论，作为**"如果将来要重新引入付费爬虫"的决策依据**，不代表当前代码状态。

| 通道 | 单价 | 结论 |
| --- | --- | --- |
| Apify sian.agency（公众号/知乎） | $0.14 startup + $0.09-0.39/item，单 run $0.23-0.53 | ⚠️ 贵，但**市面上唯一可用**的中文平台 ready-made scraper。**当前已移除** |
| Apify zhorex（B 站） | $0.005/item，无 startup | 曾切换，便宜 50×。**当前已移除** |
| FireCrawl | $16/月 5000 页 | ❌ 知乎 403 / 公众号 captcha / 小红书反爬全打不过 |
| Browserbase / Bright Data | — | ❌ 无中文 ready-made scraper，要自己写 |
| **OpenCLI（当前方案）** | **0 元** | ✅ 借本机已登录浏览器会话，反爬基本失效；需遵守节奏红线（§7.3） |
