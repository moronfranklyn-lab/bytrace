# 笔迹 ByTrace · 产品需求文档（PRD）

> 版本：v1.0 · 更新：2026-05-24
> 状态：待评审
> 文档定位：笔迹 ByTrace 立项阶段的产品需求定义。开发文档见 `ARCHITECTURE.md` / `API.md` / `DATA-MODEL.md`，技术选型见 `TECH-STACK.md`。

---

## 0. 一句话定义

**把一个模糊的写作思路，用「拆解过的博主风格」写成一篇有论证骨架的多平台成稿。**

笔迹 ByTrace 不生产信息，它生产「**你的观点在别人风格下的成稿**」。它要解决的不是「写不出来」，而是「写出来像 AI、浮于表面、没有论证纵深」。

---

## 1. 背景与问题

### 1.1 现状

AI 写作工具已经很多，但用下来有三个反复出现的问题：

| # | 问题 | 具体表现 |
| --- | --- | --- |
| 1 | **风格不可控** | 每次都要手写一大段提示词描述「我想要什么样的感觉」，写完还不像。风格没被沉淀下来，下次从零开始。 |
| 2 | **深度不够** | 模型能抓到表面特征（短句独段、数字分节、反差幽默），但抓不到论证方式。产出读起来是「平铺列举」——罗列了好几个角度，读者没有思考的纵深。 |
| 3 | **AI 味重** | 万能开场（「在这个数字化时代」「随着 AI 的飞速发展」）、报幕式过渡、段尾强行升华、空泛形容词堆砌。 |

### 1.2 判断

第 2 条是根因。**风格可以描述，但论证骨架必须被显式约束**，否则模型一定会用最省力的「并列列举」结构交差。

因此本产品的核心不是「写得更快」，而是**把写作中那些原本靠品味和经验的判断，变成结构化的数据在流程里显式流动**：

```
从「我想要半佛那种感觉」
   ↓
拆解成可复用的结构化风格指纹
（开篇套路 / 句长偏好 / 论证形态 / 物件类比库 / 收尾方式）
   ↓
每次写作时作为硬约束喂进模型
```

## 2. 目标用户与核心任务

### 2.1 目标用户

| 维度 | 描述 |
| --- | --- |
| 是谁 | 内容创作者、产品经理、独立写作者中**需要长期稳定产出长文**的那一类人 |
| 特征 | 有自己的观点和素材，但要把观点组织成有说服力的长文需要大量时间；对「AI 味」敏感 |
| 平台 | 主要在公众号 / 知乎 / 少数派 / 优设 / 小红书等中文平台发布，一篇内容常需要改写成多个平台版本 |
| 技术能力 | 能填配置文件、能开终端；但不愿意每次写文章都手搓提示词 |
| 使用频率 | 按需使用，典型节奏是「攒了几个想写的点 → 一次性拆博主 + 批量产文」 |
| 人机比 | 1:1。单用户、单机运行，无并发、无多租户 |
| 交互形态 | 同步流式。用户盯着屏幕看正文逐字产出，随时可中止 |

### 2.2 核心任务

> 把「一段思路 + 喜欢的博主风格 + 目标平台口味」变成可以直接发布的成稿。

支撑这个任务的三个子任务：

1. **学风格** —— 把喜欢的博主的文章拆成可复用的「风格指纹」。
2. **学平台** —— 把目标平台（公众号 / 知乎 / 小红书…）的板块口味拆成「站点画像」。
3. **按骨架写** —— 先出有论证骨架的大纲（每节有 thesis 和 depth_role），确认后再流式扩写成正文。

### 2.3 明确不服务的场景

- 多人协作 / 团队共用（无账号体系、无并发控制）
- 对外提供 SaaS 服务
- 自动发布到平台（只产出成稿 + 导出格式，发布动作留给人）
- 无节制批量抓取（见 §7.3 平台边界）

## 3. 输入、过程与产物

### 3.1 输入

**三份必需原料**：

| 原料 | 从哪来 | 形态 | 耗时 | 复用性 |
| --- | --- | --- | --- | --- |
| **① 风格指纹** | 粘 3–5 篇目标博主文章，或贴主页 URL 自动抓取 | 结构化 JSON | 40 秒 ~ 8 分钟 | **一次拆解，长期复用** |
| **② 站点画像** | 贴板块 URL 自动爬，或手贴文章 | 结构化 JSON（板块级 + 编辑级） | ~2 分钟 | 可加样本迭代 |
| **③ 选题思路** | 手写一段话，或从选题中心挑一条 | 一段自由文本（题材 + 角度 + 核心观点） | 1 分钟 | 一次性 |

**三份可选弹药**：

| 弹药 | 从哪来 | 作用 |
| --- | --- | --- |
| **④ 事实底座** | 思路确认后自动后台联网搜集 | 给大纲/正文喂真实数字与来源，**防止模型编造数据**。搜索不可用时自动跳过，不阻塞主流程 |
| **⑤ 风格配方** | 从跨博主碎片库里挑碎片组合并命名保存 | 实现「开篇用 A 博主 + 论证用 B 博主 + 收尾用 C 博主」 |
| **⑥ 参考素材** | 手动粘贴的调研材料 / 旧文 | 注入写作上下文 |

### 3.2 过程：七步，两个人工确认闸门

| 步 | 名称 | 用户做什么 | 系统做什么 |
| --- | --- | --- | --- |
| 1 | 选目标平台 | 选主平台，可顺手勾选要同时出的其他平台版本 | 展示已拆解的站点画像卡片 + 通用平台画像兜底 |
| 2 | 题材思路 | 写一段思路 | 收下选题，**并立即在后台起跑事实底座搜集** |
| 3 | 推荐风格 | 从推荐里挑，或去指纹库自选 | 按题材推荐匹配的指纹 / 配方 |
| 4 | 微调组合 | 挑风格配方、补充要求 | 拼装自定义要求 |
| 5 | 生成大纲 | **看大纲、确认论证骨架** | 产出核心论点 + 结构形态 + 每节 thesis 与 depth_role |
| 6 | 流式正文 | 盯着看，不满意可中止 | 多平台串行流式生成 → 每篇自动评分 → 不达标带建议重写 |
| 7 | 预览导出 | 选导出格式 | 公众号 HTML / Markdown / 小红书长图 / 纯文本 |

**闸门 A（第 2 步）**：思路一确认就 fire-and-forget 起跑后台事实搜集；到第 5 步之前通常已就绪，未就绪时第 5 步会软等待，用户可点「不等了」跳过。

**闸门 B（第 5 步）**：全流程唯一强制的结构确认点。大纲每节必须标注 `depth_role` ∈ `open` / `deeper` / `parallel` / `turn` / `close`，且**整篇至少一节 `deeper`、禁止全 `parallel`**——这是为了从结构上逼出论证纵深，而不是平铺列举。

### 3.3 产物

| 产物 | 是否长期保留 |
| --- | --- |
| 文章正文（可含多平台版本） | ✅ |
| 平台版本差异摘要 | ✅ |
| 风格指纹（含样本、类别细分配方） | ✅ |
| 站点画像 | ✅ |
| 风格配方 | ✅ |
| 事实素材包（按选题哈希缓存，省重复联网） | ✅ |
| 导出的成稿文件 | 由用户自行保存 |
| 配图关联 | ✅ |

## 4. Agent 主链路

### 4.1 链路形态

**分步确认式**，不是一次生成，也不是自由多轮对话：

```
选平台 → 写思路 →[确认]→ 挑风格 → 微调 → 出大纲 →[确认]→ 流式正文 → 预览导出
                                          ↑
                                    唯一强制闸门
```

### 4.2 三条子链路

#### ① 风格指纹拆解

**多阶段流水线 + 多篇并行**：

| 阶段 | 做什么 | 超时 |
| --- | --- | --- |
| Stage 0 | 文章自动分类（8 个固定类别白名单，**不让模型自由分类**，避免类别碎片化） | 常规 |
| Stage 1 | 逐篇抽取：多维度风格特征 + 结构形态 + 挖根层次 + 具象类比 | 常规 |
| Stage 2 | 汇总成结构能力库 + 挖根模式 + 物件类比库 | 480s |
| Stage 3 | 跨平台对比报告 | 360s |
| 类别配方 | 单类别样本 ≥ 3 篇时，生成该类别专属配方 | 360s |

**关键约束**：类比必须**物件级**（「户口本进 iCloud」），禁止抽象隐喻（「如同登山」不算）。

#### ② 写作链路

- **大纲**：流式产出。必须给出核心论点 + 结构形态 + 每节 thesis 与 depth_role。
- **正文**：流式产出，**多平台串行**（不并发——订阅制通道并发会撞限速）。单平台失败不阻断后续平台。
- **评分回炉**：每篇正文落地后自动五维评分，不达标则带具体建议**全文重写**；用完次数仍不达标则按总分选最优稿兜底。评分失败时 **fail-open**，不阻塞交付。

#### ③ 事实底座

思路确认即后台起跑，联网搜集真实事实 / 数据 / 反方观点 / 来源，注入大纲与正文。

**有素材包时的强约束**：正文里所有具体数字、人名、事件、引用**必须**来自素材包，禁止凭空编造；没有的宁可用定性描述。没有素材包时 prompt 自动降级，等同于不启用该能力。

### 4.3 哪些步骤必须用户确认

| 确认点 | 强制？ | 不确认的后果 |
| --- | --- | --- |
| 第 2 → 3 步（思路确认） | ✅ 强制 | 没有选题无法往下走 |
| 第 5 → 6 步（大纲确认） | ✅ 强制 | **唯一论证骨架闸门**，跳过等于放弃深度控制 |
| 第 6 步中途中止 | 可选 | 中止后可重新生成 |
| 事实底座等待 | 软等待 | 可点「不等了」跳过，prompt 自动降级 |

## 5. 什么算「生成得好」

### 5.1 机器可判的标准

正文落地后自动按五维评分，每维 0–5 分，满分 25：

| 维度 | 判什么 |
| --- | --- |
| **结构** | 结构形态是否贯彻；depth_role 是否有 `deeper` 且非全 `parallel` |
| **深度** | 是否沿读者问题链下钻，而不是平铺列举 |
| **类比** | 是否用了博主类比库里的**具象物件**，而非抽象隐喻 |
| **金句** | 是否有记忆点、不堆砌、且不超过正文证据力度 |
| **禁忌** | 是否触犯 AI 腔、是否编造第一人称经历或实测结果、是否有装饰符号 |

阈值 **20 / 25**。不达标带建议重写，最多 3 次（首次 + 2 次重写），仍不达标则按总分取最优稿。

### 5.2 定性的好稿标准

1. **洞察解释真实矛盾**，而不是把行业共识换个说法。
2. **每节首段回扣上节论断**，沿同一条问题链下钻，并交付新的理解 / 选择 / 行动 / 验证收益。
3. **抽象论点必须配物件级类比**——这是本产品的灵魂底线。
4. **第一人称只承担真实亲历、判断与选择责任**，不编造动作、情绪、对白、现场细节。
5. **没有 AI 腔**：没有报幕式过渡、段尾升华、万能暖场、空泛形容词、重复判断。
6. **事实后立即给判断**；数据补口径；失败写完整（预期 → 现象 → 根因 → 修复 → 新规则）。
7. **标题承诺不超过正文证据**；结尾回扣核心矛盾，不突然上升成时代宣言。

### 5.3 允许的瑕疵

| 瑕疵 | 容忍度 |
| --- | --- |
| 个别标点 / 排版错误 | 可接受（导出后可手改） |
| 未通过阈值的稿子 | 会保留并标记评分（不阻塞交付） |
| 事实数字有出入 | **不可接受** → 因此有事实底座 + 强制来源标注 |
| 编造第一人称经历 | **红线** |
| 抽象隐喻偷懒 | **红线** |

### 5.4 谁来判断

| 判断者 | 判什么 |
| --- | --- |
| **审查模型** | 日常自动把关：五维评分，不达标自动重写 |
| **用户** | 最终判断：第 5 步看大纲、第 6 步盯流式、第 7 步看预览。**只有用户有权说「这篇可以发」** |

## 6. 交付阶段与优先级

### 6.1 阶段规划

| 阶段 | 目标 | 交付内容 |
| --- | --- | --- |
| **M0 脚手架** | 跑通工程骨架 | 框架 + 数据库基础表 + 三主题 + 构建通过 |
| **M1 指纹闭环** | 「粘 3–5 篇文 → 出风格指纹 → 看详情」端到端 | 指纹拆解（流式）+ 指纹列表与详情页 |
| **M2 写作闭环** | 「一段思路 → 出正文 → 导出」端到端 | 大纲 / 正文 / 润色流式 + 站点画像 + 风格配方 + 多平台出稿 + 导出 |
| **M3 深度增强** | 解决「浮于表面」 | 结构能力库 + 挖根模式 + 物件类比库，并贯通到大纲与正文提示词 |
| **M4 质量闭环** | 自动把关质量 | 五维评分 + 不达标回炉重写 + 最优稿兜底 |
| **M5 事实增强** | 解决「数字不可信」 | 事实底座联网搜集 + 注入 + 强制来源标注 |
| **M6 工程收口** | 可交付、可换供应商 | 环境变量分组外置 + 健康自检 + 部署文档 |

### 6.2 优先级原则

- **先把一条链路做通再铺开**：核心链路未验证前不做正式 UI 打磨。
- **只做需求触发的模块**：不为「技术栈完整」引入用不到的组件。
- **不可逆操作要有人工闸门**：删除类操作两段式确认。

## 7. 模型与成本约束

### 7.1 模型分工

产品按**任务类型**分组配置模型，而不是一个开关切全应用：

| 任务组 | 用途 | 特点 |
| --- | --- | --- |
| **主 Agent** | 大纲 / 正文 / 润色 / 指纹拆解 / 分类 | 分析类与正文类可分设不同模型：正文用更擅长中文表达、AI 味更低的模型 |
| **审查模型** | 五维评分、事实审查 | **刻意与写作模型不同**，见 §7.2 |
| **联网事实搜索** | 事实底座搜集 | 可与主 Agent 同源（模型自带联网插件），也可独立接搜索 API |

### 7.2 为什么审查要单独一个模型

**同模型自审容易认同自己的输出。** 换一个模型来挑刺会狠很多——它能揪出写作模型自己发现不了的硬伤（错误合成的数字、证据外推等）。

因此产品把「审查模型」做成独立可配的一组：写作走 A 家、审查走 B 家。

### 7.3 平台边界（写进代码的硬约束）

抓取外部内容时遵守真人浏览节奏，禁止行为：

- 🚫 定时高频轮询
- 🚫 短时间连续大量批量抓取
- 🚫 纯「只看不互动」的异常行为模式
- 🚫 跨账号操作

**adapter 层强制节奏**（不可绕过）：

| 平台 | 每条间隔 | 单日单账号上限参考 |
| --- | --- | --- |
| 公众号 | 1 秒 | 100+ 篇 |
| B 站 | 5 秒 | 30–50 条 |
| 知乎 | 8 秒 | 20–30 条 |
| 小红书 | 15 秒 | 10–20 条 |
| 抖音 | 30 秒 | 10 条 |

产品当前的主要使用场景（拆指纹单次 ≤ 20 篇）都在安全区内。

### 7.4 成本约束

| 项 | 要求 |
| --- | --- |
| 模型调用 | 优先复用已有订阅；支持按任务组外置为 API，按量计费可控 |
| 长任务超时 | 重负载调用必须显式设置超时（拆解类最高 8 分钟，正文每平台 8 分钟，评分 2 分钟） |
| 联网搜索 | 三档成本：模型自带联网插件（含在订阅内）> 独立搜索 API（按次）> 免密钥兜底（免费） |
| 预算护栏 | 需要能一眼看出「本次调用花了多少」，且任一组可单独停用 |

## 8. 数据与非功能要求

### 8.1 数据与隐私

| 项 | 要求 |
| --- | --- |
| 数据位置 | **全部存在本机**，单文件数据库 |
| 是否上云 | 不上云，不做 SaaS |
| 多租户 | 不支持，单用户单机 |
| 密钥管理 | 只写在本地环境文件里，不进代码、不进前端产物、不进版本库、不在日志与对话中回显 |
| 敏感数据 | 用户的文章语料、拆解过的博主样本、未发布草稿 |
| 出境风险 | ⚠️ 使用外部模型 API 时，投喂的选题与正文会离开本机。**产品必须让用户明确知情，并始终保留「全部走本机」的选项** |

### 8.2 性能

| 项 | 目标 |
| --- | --- |
| 正文生成 | 流式首字尽快返回；长任务用 SSE 心跳防止连接超时 |
| 指纹拆解 | 单阶段最长 8 分钟，必须有阶段进度反馈 |
| 并发 | 不追求并发。多平台刻意串行，避免触发上游限速 |
| 数据规模 | 单用户量级，单文件数据库完全够用 |

### 8.3 安全边界

| 边界 | 要求 |
| --- | --- |
| 文件访问 | 素材扫描限定在白名单根目录 |
| 设置写入 | key 名与取值双向白名单校验 |
| 破坏性操作 | 删除类操作两段式确认 |
| 错误信息 | 统一错误结构，**不泄露堆栈** |
| 服务暴露 | 只绑定本机回环地址 |

## 9. 上线与交付形态

| 项 | 结论 |
| --- | --- |
| 谁用 | 本地单用户 |
| 登录 | 无登录。靠「本机回环地址 + 单用户」物理隔离 |
| 云平台认证 | 不需要（不上云） |
| 云费用 | 0（本机运行） |
| 交付形态 | 本机安装 + 双击启动器；数据落在用户主目录的标准位置 |
| 后续形态 | 套壳为原生桌面应用（独立窗口、Dock 图标、安装包） |

## 10. 风险与应对

| # | 风险 | 应对 |
| --- | --- | --- |
| R1 | 模型抓不到「论证形态」这个抽象特征 | 拆解阶段就把它显式提取为独立字段，并强制大纲输出结构形态与每节 depth_role |
| R2 | 大纲全是并列结构，正文必然平铺 | 提示词层硬禁止「全 parallel」，并要求至少一节 deeper |
| R3 | 类比写成抽象隐喻（「如同登山」） | 拆解阶段只收物件级类比；评分维度单独考核类比 |
| R4 | 模型编造数据与来源 | 事实底座 + 「有素材包时必须来自素材包」的强约束 + 强制来源标注 |
| R5 | 自审偏松 | 审查模型独立可配，刻意与写作模型分离 |
| R6 | 长任务超时导致半截结果 | 分级超时 + 心跳 + 失败不阻塞交付（fail-open） |
| R7 | 用户密钥泄露 | 密钥只落本地环境文件；自检端点只报告「有没有」，绝不回显值 |
| R8 | 换电脑 / 换环境后跑不起来 | 环境变量分组外置 + 自检端点 + 不硬编码任何机器路径 |
