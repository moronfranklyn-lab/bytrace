# 笔迹 ByTrace · 作品介绍

> 一句话：**把一个模糊的写作思路，用「拆解过的博主风格」，写成一篇有论证骨架的多平台成稿。**
>
> 形态：本地运行的单用户应用（Next.js + SQLite + 模型可换），从需求定义、架构设计到部署交付独立完成。

---

## 一、我在解决什么问题

市面上 AI 写作工具我用了不少，反复撞到三堵墙：

| # | 问题 | 具体表现 |
|---|---|---|
| 1 | **风格不可控** | 每次都要手打一大段提示词描述"我想要什么感觉"，写完还是不像。风格没被沉淀，下次从零开始。 |
| 2 | **深度不够** | 模型学到了表面特征（短句独段、数字分节、反差幽默），但学不到论证方式。产出是"平铺罗列"——列了好几个角度，读者没有思考的纵深。 |
| 3 | **AI 味重** | 万能开场（"在这个数字化时代"）、报幕式过渡、段尾强行升华、空泛形容词堆砌。 |

我判断**第 2 条是根因**。风格是可以被描述的，但论证骨架如果不被显式约束，模型一定会用最省力的"并列列举"结构交差。

所以这个产品的核心不是"写得更快"，而是：

> **把写作中那些原本靠品味和经验的判断，变成结构化的数据，让它在流程里显式流动。**

```
「我想要半佛那种感觉」
        ↓  拆解
风格指纹：开篇套路 / 句长偏好 / 论证形态 / 物件类比库 / 收尾方式
        ↓  每次写作作为硬约束喂进模型
```

## 二、产品怎么做的

### 2.1 三份原料

| 原料 | 输入 | 产出 | 复用性 |
|---|---|---|---|
| **风格指纹** | 粘 3–5 篇目标博主的文章 | 多维风格特征 + 结构能力库 + 挖根模式 + 物件类比库 | 一次拆解，长期复用 |
| **站点画像** | 贴一个板块 URL | 板块级 + 编辑级口味画像 | 可加样本迭代 |
| **选题思路** | 写一段话 | 驱动的输入 | 一次性 |

### 2.2 七步流程，两个人工闸门

```
选平台 → 写思路 →[确认]→ 挑风格 → 微调 → 出大纲 →[确认]→ 流式正文 → 预览导出
                                          ↑
                                    唯一的强制闸门
```

**第 5 步的大纲确认是全流程唯一强制的闸门**，也是「平铺列举」和「层层下钻」的分水岭。

大纲里每一节必须标注它在整篇论证中扮演什么角色（`open` / `deeper` / `parallel` / `turn` / `close`），并且硬性禁止整篇都是并列——**至少有一节必须真的往下挖一层**。

### 2.3 四条关键机制

**① 物件级类比**
拆解阶段只收**具象物件**（"户口本进 iCloud"），明确拒收抽象隐喻（"如同登山"不算）。类比是单独一个评分维度，会被反复考核。

**② 评分回炉（reflection loop）**
正文落地后自动五维评分——结构 / 深度 / 类比 / 金句 / 禁忌，各 0–5 分、满分 25、阈值 20。不达标就带着**具体修改建议全文重写**，最多 3 轮；仍不达标则按总分取最优稿兜底。评分器故障时不阻塞交付。

**③ 跨模型审查**
**审稿和写作刻意不是同一个模型。** 同模型自审容易认同自己的输出；换一个模型来挑刺会狠很多。这一组配置独立可换，实现"写作走 A 家、审查走 B 家"。

**④ 事实底座**
选题确认后自动在后台联网搜集真实事实与来源，注入大纲与正文。有素材包时**强制约束**：正文里所有具体数字、人名、事件、引用必须来自素材包，禁止编造；没有的宁可用定性描述。搜索不可用时自动跳过，不阻塞主流程。

## 三、我做的几个关键判断（这部分是重点）

### 判断 1：不做通用 Agent，做领域专用载具

通用 Agent 有十几个标准组件（工具系统、记忆、任务规划、子 Agent、定时调度、MCP……）。我只选了需要的 6 个，并明确记录了**每个不选的理由**：

| 组件 | 结论 | 理由 |
|---|---|---|
| 工具系统 | 选 | 需要抓取与素材检索 |
| 子 Agent | 选 | 指纹拆解时多篇文章并行，上下文隔离省 token |
| 技能加载 | 选 | 写作方法论按需注入，不整篇塞进上下文 |
| 记忆系统 | 选（领域形态） | 指纹 / 画像 / 配方就是本产品的记忆，是**结构化**的，不是通用记忆 |
| 后台任务 | 选 | 事实底座后台起跑，不阻塞主流程 |
| 目标闭环 | 选 | 用评分回炉实现"独立判断器审查是否达标" |
| **定时调度** | **明确不选** | 抓取红线第一条就是禁止定时高频轮询——**主动放弃这个能力** |
| MCP 插件 | 不选 | 外部能力直接集成适配器；单机项目引入 MCP 只增加故障面 |
| 上下文压缩 | 不选 | 每次调用是独立提示词，不累积长会话 |

> **这个"不选清单"本身就是设计决策。** 它是领域专用载具，不是通用平台——用"写作领域该有的机制"替换掉"通用 Agent 该有的机制"。

### 判断 2：把"品味"翻译成可以编程约束的东西

这是整个项目最核心的一步。

"文章要有深度"是无法执行的指令。但如果把它拆成：
- 大纲每节必须带 `depth_role`
- 整篇至少一节 `deeper`，禁止全 `parallel`
- 每节首段必须回扣上一节的论断
- 抽象论点必须配一个博主类比库里的**具象物件**

……它就变成了四条可以写进提示词、可以被评分器检查的硬约束。

**我的方法论：凡是"感觉不对"的反馈，都要往下追一层，追到能被结构化表达为止。**

### 判断 3：审查必须换一个模型

同模型自审的问题不是能力不够，而是**倾向性偏差**——它倾向于认为自己写得对。

所以我没把精力花在"把评分提示词写得更严"，而是花了很小的成本引入**第二个模型**做审查。这是一个结构性解法，而不是调参。

### 判断 4：长任务必须可中断、可降级、不阻塞

写作是分钟级的长任务，实测某些阶段单次可以跑 5–8 分钟。我按任务分级设置超时，长任务用事件流保活，并且让每个可选环节**优雅降级**：

- 联网搜索不可用 → 跳过，正文照常生成
- 评分器故障 → 用当前稿落库，不阻塞交付
- 某个平台失败 → 其余平台继续，失败项单独回报

**用户不应该因为一个非核心环节出问题就拿不到结果。**

## 四、技术形态与关键取舍

| 层 | 选择 |
|---|---|
| 交互 | Next.js App Router（18 个页面）+ SSE 流式 |
| 编排 | 拆解引擎 / 评分回炉循环 / 事实底座编排 |
| 模型 | 统一模型入口，支持本机 CLI、OpenAI 兼容、Responses 三种通道 × 三个任务分组 |
| 数据 | SQLite（WAL），单文件，全本机 |
| 桌面 | Electron 外壳 + 本机服务，独立窗口 |

**几个刻意的"不"：**

- **不接厂商 SDK**：优先复用已订阅通道，避免同一份能力付两次费；接口层自己做，反而换供应商更容易
- **不上云、不做 SaaS**：单用户单机，零运维
- **不引 UI 组件库**：用 CSS 变量做三套主题（牛皮纸·朱砂 / 夜书房·鎏金 / 极简·松石青），保持书卷气
- **多平台刻意串行而非并发**：避免触发上游限速

**可移植性上吃过亏，所以定了硬规矩**：不允许出现任何硬编码的机器路径。CLI 位置按用户主目录推导 + 环境变量覆盖，找不到时报错要列出"已经试过哪些路径"。

## 五、交付形态

从「装不上」到「双击就用」，这条链路我也完整做了：

| 入口 | 作用 |
|---|---|
| **安装笔迹.command** | 检查运行环境 → 装依赖 → 生成配置 → 体检 → 装桌面图标 |
| **填写API密钥.command** | 打开配置填密钥，并自动检查是否填好 |
| **启动笔迹.command** | 挑可用运行时 → 端口检测 → 起服务 → 开窗口 → 打印自检结果 |
| **独立窗口应用** | Electron 外壳，有自己的图标、Dock 图标与菜单 |

**顺带解决了一个很隐蔽的环境问题**：机器上常同时存在多个来源的运行时，它们的版本号与内部 ABI 不一定一致，而数据库依赖是按固定 ABI 编译的原生模块——**选错解释器就启动崩溃，报错还完全指不到原因**。

我的解法不是猜版本号，而是**对每个候选运行时真的执行一次「能不能加载数据库」**，能通过才算可用。这是唯一可靠的判定方式。

## 六、过程与踩坑记录

这个项目我全程保留了工程记录（架构决策、每个"为什么不"、踩过的坑）。几个有代表性的：

| 坑 | 根因 | 解法 |
|---|---|---|
| 流式输出"假流式" | 命令行默认不流式，整篇答完才吐出来，用户盯着"已 0 字"等 100 秒 | 改用结构化流式协议，首字节从 100 秒降到 5 秒 |
| 环境变量里有个开关让桌面外壳退化成普通运行时 | 宿主环境导出了一个变量，导致二进制不再提供桌面能力，报错完全指不到原因 | 启动包装器显式清掉它 |
| 评分器故障时反而丢稿 | 评分失败后"最优稿兜底"逻辑用更早的低分稿顶掉了用户刚看完的新稿 | 加"未评分"标记，禁止顶掉 |
| 界面数字与数据库不一致 | 首页配图数量是写死的文案，实际库里有 21 张却显示 247 | 改成读真实计数 |
| 图标打包工具在中文路径下失败 | 工具本身对非 ASCII 路径的处理有问题 | 先复制到临时目录打包再移回 |

> 我习惯把根因写进代码注释和文档，因为**同一个坑会以不同形式再出现一次**。

## 八、可以直接用的一句话（简历 / 作品集摘要）

> **笔迹 ByTrace — 本地 AI 写作工具（独立完成产品与实现）**
> 解决 AI 写作"风格不可控、论证浮于表面、AI 味重"的问题。核心思路是把写作中靠品味的判断转成结构化数据：把博主文章拆成「风格指纹」，在流程里用「论证骨架」硬约束模型（每节标注论证角色、禁止平铺罗列），并引入**第二个模型做跨模型审查**替代自审。覆盖风格拆解、多平台成稿、事实底座、五维评分回炉五条链路，交付为可双击启动的桌面应用。
